Update the Dirty 30 beta to use phone-number-based authentication instead of email-based authentication.

This requirement supersedes every earlier instruction that uses email as the authentication identifier, invitation identity, or commissioner bootstrap identity.

Preserve the existing Clerk, React/Vite, Express, PostgreSQL, Drizzle, OpenAPI, and Replit architecture.

Authentication experience

Use Clerk phone authentication with SMS one-time verification codes.

The beta must support:

* Sign up with phone number
* SMS verification during sign-up
* Sign in with phone number
* SMS one-time verification code during sign-in
* Sign out
* Session restoration
* Expired or incorrect code handling
* SMS resend handling and cooldown messaging
* Loading and connection-error states

Do not use passwords.

Do not offer email, username, social login, or password authentication in the beta interface.

Do not create a separate SMS implementation. Clerk must send and verify the one-time codes.

Use Clerk’s supported prebuilt components unless a custom flow is necessary to enforce the phone-only experience. Keep the authentication screens consistent with the existing Dirty 30 mobile design.

Clerk configuration requirement

Verify and document that the Clerk application must have:

* Sign-up with phone enabled
* Phone required at sign-up
* Phone verification required at sign-up
* Sign-in with phone enabled
* SMS verification code enabled
* United States enabled in the SMS country allowlist
* Email and password strategies disabled for this beta

Do not claim these Clerk Dashboard settings were changed unless they were actually changed through an available integration. If they require manual configuration, provide exact dashboard steps in the completion report.

Production SMS authentication may require a paid Clerk plan. Report this requirement clearly.

Phone-number normalization

Store and compare all phone numbers in E.164 format.

For example:

+18155551234

Use a maintained phone-number parsing and validation library. Do not implement phone normalization with custom string replacement alone.

The interface may display a friendly formatted number, but database storage, uniqueness checks, invitation matching, authentication matching and authorization must use E.164.

Reject invalid or unsupported phone numbers before creating an invitation.

Database changes

Update the User model:

* phone becomes required, normalized and unique.
* email becomes optional.
* Add an index or unique constraint for normalized phone.
* Preserve externalAuthId as the unique Clerk user identifier.

Update PlayerInvitation:

* Replace invitedEmail with required invitedPhone.
* Store the phone in normalized E.164 format.
* Prevent duplicate pending invitations for the same team and phone number.

Generate a reviewed migration that safely handles the existing development records. Because existing seeded .local email records may not have usable phone numbers, update or replace development seed records without inventing production user data.

Do not silently delete real production users. If existing production records lack phone numbers, stop and report the required migration decision.

Commissioner bootstrap

Replace:

BOOTSTRAP_COMMISSIONER_EMAIL

with:

BOOTSTRAP_COMMISSIONER_PHONE

The configured value must be an E.164 phone number.

The first verified Clerk account whose verified primary phone matches BOOTSTRAP_COMMISSIONER_PHONE may become commissioner.

Never assign commissioner status using an unverified number, browser-provided value or request body.

Remove the email bootstrap logic after the phone bootstrap is verified.

Backend identity resolution

Update the Clerk user-resolution middleware to:

1. Require an authenticated Clerk user.
2. Retrieve the verified primary phone number from Clerk.
3. Reject accounts without a verified primary phone.
4. Normalize the phone to E.164.
5. Resolve the application user by externalAuthId first.
6. Link an existing invited user only when the verified phone exactly matches.
7. Never overwrite another user’s identity because of an unverified or duplicate number.
8. Store optional email only when Clerk provides a verified email.

Never trust a phone number supplied by the frontend as proof of identity.

Phone-based roster invitations

Change roster invitations from email to phone number.

Captain or commissioner workflow:

* Enter player phone number
* Validate and normalize it
* Check roster capacity
* Create invitation
* Copy a secure invitation link
* Cancel invitation
* Regenerate invitation link
* View the friendly formatted phone number in the pending roster

Player workflow:

* Open invitation link
* Sign up or sign in using the invited phone number
* Verify the phone through Clerk SMS
* Accept the invitation
* Join the roster

Invitation acceptance must compare the invitation’s E.164 number with the authenticated user’s verified Clerk phone number.

The invitation token remains random, hashed, expiring and single-use.

Actual invitation-link delivery by SMS is not required yet. The captain can copy and manually send the invitation link. Clerk remains responsible only for authentication OTP messages.

Player profile

Basic player information becomes:

* First name
* Last name
* Verified phone number
* Optional email address

Users cannot directly change the application’s verified phone field to an unverified number.

Phone-number changes must occur through Clerk’s verified phone-management workflow and synchronize only after verification.

OpenAPI and interface

Update the OpenAPI specification before regenerating clients and Zod validators.

Replace invitation email fields, labels, placeholders, validation messages and documentation with phone-number equivalents.

Remove all beta authentication language that instructs users to sign in through email or password.

Use phone-friendly input behavior:

* type="tel"
* Appropriate autocomplete attributes
* United States as the initial country selection
* Clear country code display
* Friendly formatting while typing
* E.164 storage after validation

Do not expose complete phone numbers unnecessarily in league-wide views. Full phone numbers may be visible only where roster-management permissions require them.
